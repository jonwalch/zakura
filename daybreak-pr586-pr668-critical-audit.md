## Critical findings

### DB-CRIT-001 — Four version races discard deterministic invalid-body evidence and terminate native sync

- **Class:** Critical operational failure
- **Confidence:** High
- **Production reachability:** Testnet
- **Affected revisions:** Introduced by PR #586 commit [`90683a40e1a5055982dc6a05f7198361bfe49e7f`](https://github.com/zakura-core/zakura/commit/90683a40e1a5055982dc6a05f7198361bfe49e7f) and present at audited head `139c4d1c3269421f616275986e760f23f4560925`. PR #668 is not the source.
- **Location:** [`block_sync_driver.rs` stale bound and terminal outcome](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakurad/src/commands/start/zakura/block_sync_driver.rs#L736-L797), [`block_sync_driver.rs` driver shutdown](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakurad/src/commands/start/zakura/block_sync_driver.rs#L313-L359), [`sequencer_task.rs` version snapshot](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-network/src/zakura/block_sync/sequencer_task.rs#L730-L744), [`request.rs` version-only prepared evidence](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-state/src/request.rs#L959-L971), and [`replay.rs` global-version admission](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-header-chain/src/transition/planner/replay.rs#L63-L74).
- **Violated contracts:** `LC-BODY-02`, `LC-ACCEPT-04`.
- **Trigger:** A Testnet peer supplies a body that reproduces its selected header's commitments but deterministically fails a body/state consensus rule. While that verifier completion is being persisted, the attacker or concurrent header peers keep at least one valid header-target insertion queued ahead of each refreshed evidence request. One insertion before the initial request and one before each of the three retries advances the global state version four times.
- **Failure path:**
  1. The sequencer correctly checks the live body owner, source, token, hash, and semantic currency, but emits `RecordBodyInvalid` with only the then-current global `state_version`.
  2. `from_full_verifier` seals the intrinsic evidence with that version but no body-work owner. `TransitionEvent::body_owner()` recognizes only `AuxEvidence`, so consensus-invalid body evidence takes the global compare-and-swap path.
  3. Header insertions and invalid-body evidence share the same serialized non-finalized writer queue. Authenticated header insertions deliberately ignore the global version and each effective insertion advances it; invalid-body evidence requires exact equality.
  4. The queue schedule returns `Stale(v+1)`, commits another header, returns `Stale(v+2)`, commits another header, and so on. On the fourth stale receipt, `stale_refreshes >= 3` returns `FailedClosed("stale_refresh_exhausted")` without committing the evidence.
  5. The main action loop cancels pending applies, drains in-flight applies, and returns. The production task is spawned once and merely retained for shutdown; there is no monitor or restart path.
  6. In `network.p2p_stack = "zakura"`, the watchdog has no legacy fallback and continues warning forever. The body-invalid branch remains durably unmarked and native body sync makes no further progress.
- **Impact:** Deterministic consensus-invalid evidence is lost, which is itself a critical threshold outcome. The sole native body-sync driver then stops for the process lifetime. Restart does not recover the missing evidence, and a peer can repeat the same schedule after restart.
- **Evidence:** [`ConsensusBodyInvalid` has no owner coordinate](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-header-chain/src/transition/types/event/mod.rs#L169-L175); [`NonFinalizedWriteMessage` serializes both insertions and evidence](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-state/src/service/write.rs#L1480-L1507), and the worker handles them on the same receive loop ([insert](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-state/src/service/write.rs#L2286-L2313), [invalid evidence](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-state/src/service/write.rs#L2322-L2328)). Every effective transition increments `state_version` ([write-set derivation](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-header-chain/src/transition/planner/write_set.rs#L105-L122)), and up to 16 target operations may already be staged ([limit](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-header-chain/src/config.rs#L22-L27)). The driver is spawned only once ([`start.rs`](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakurad/src/commands/start.rs#L514-L544)); task ownership only joins it during endpoint shutdown ([`handler.rs`](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-network/src/zakura/handler.rs#L631-L671)). The existing regression proves only one stale-to-success refresh ([test](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakurad/src/commands/start.rs#L2823-L2934)).
- **Reproduction:** Use the existing `block_sync_driver_refreshes_stale_consensus_invalid_body_evidence` harness with a deterministic mock writer that returns four successive `ApplyResult::Stale` receipts whose `current_version` values increase by one. Assert that the driver `JoinHandle` completes before its shutdown signal and that the mock observes no `Committed` response. A full integration variant queues one valid `ApplyHeaderChainInsert` before each evidence attempt. No source was modified during this audit.
- **Fix direction:** Make intrinsic `ConsensusBodyInvalid` persistence immune to unrelated global-version churn. The serialized writer should rebind the exact hash/evidence against its current durable snapshot and commit the invalidity/tombstone idempotently, while still rejecting a mismatched hash or conflicting evidence. A bounded retry that exits only the sole driver is not an acceptable substitute for the required durable transition.

### DB-CRIT-002 — The v8-only cutover permanently strands v7-only Zakura deployments

- **Class:** Critical operational failure
- **Confidence:** High
- **Production reachability:** both
- **Affected revisions:** Introduced by PR #586 commit [`ebb60ab2d86c3ead2db833173fde2771def35f40`](https://github.com/zakura-core/zakura/commit/ebb60ab2d86c3ead2db833173fde2771def35f40) and present at audited head `139c4d1c3269421f616275986e760f23f4560925`. PR #668's extracted contracts are unchanged and are not the source.
- **Location:** [`service.rs` declares only bit 5/version 8](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-network/src/zakura/header_sync/service.rs#L33-L44), [`handler.rs` explicitly rejects version 7 and retired bit 4](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-network/src/zakura/handler.rs#L8289-L8304), [`start.rs` disables fallback for Zakura-only mode](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakurad/src/commands/start.rs#L792-L805), and [`sync.rs` waits forever when fallback is disabled](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakurad/src/components/sync.rs#L1218-L1227).
- **Violated contracts:** `LC-V7-01`, `LC-V7-03`, `LC-ACCEPT-01`.
- **Trigger:** Start or restart a supported Mainnet or Testnet node with `network.p2p_stack = "zakura"` from a fresh or behind state while every reachable native peer is still on current `main`/v7. This is the ordinary first-canary state of a rolling deployment: base peers advertise header-sync capability bit 4 and stream version 7, while the upgraded node advertises only bit 5/version 8.
- **Failure path:**
  1. Base `main` offers [bit 4](https://github.com/zakura-core/zakura/blob/ac3078c0c06fc3868a10c38b7633d9d215e0b42f/crates/zakura-network/src/zakura.rs#L63-L70) and [stream version 7](https://github.com/zakura-core/zakura/blob/ac3078c0c06fc3868a10c38b7633d9d215e0b42f/crates/zakura-network/src/zakura/header_sync/wire.rs#L3-L17). The new node offers only bit 5/version 8, so capability intersection opens no kind-5 header-sync stream.
  2. The repaired registry can select the highest common alternative, but the production header-sync service supplies an array of length one; there is no v7 alternative to select.
  3. Stream-6 block sync cannot repair this absence. Its needed-body query is derived from the local selected-header projection ([selection](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-state/src/service.rs#L1727-L1756), [empty-above-tip result](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-state/src/service.rs#L1769-L1803)); block sync does not create the missing historical header path from peer body status.
  4. `P2pStack::Zakura` is a supported production-binary configuration on both networks, but it has no legacy TCP peer set. The stall watchdog therefore selects `WarnOnly`, never legacy ChainSync, and loops indefinitely.
- **Impact:** A fresh node, a node returning after sufficient downtime, or a rolling-upgrade canary cannot discover or validate the valid greatest-work suffix and cannot catch up until a v8 peer appears or an operator changes the networking mode. That is a deterministic, process-persistent sync halt under normal rolling-upgrade conditions.
- **Evidence:** The requested normative authority says that v8 is a breaking successor whose negotiation advertises supported versions and selects one codec ([section 5.1](https://github.com/zakura-core/zakura/blob/ac3078c0c06fc3868a10c38b7633d9d215e0b42f/docs/specs/fork-aware-header-chain-engine.md#L372-L380)), then requires the v7 compatibility/fallback behavior in [`LC-V7-01..04`](https://github.com/zakura-core/zakura/blob/ac3078c0c06fc3868a10c38b7633d9d215e0b42f/docs/specs/fork-aware-header-chain-engine.md#L498-L506). Its required acceptance matrix includes `P7-01 v7_compatibility` ([section 7.2](https://github.com/zakura-core/zakura/blob/ac3078c0c06fc3868a10c38b7633d9d215e0b42f/docs/specs/fork-aware-header-chain-engine.md#L577-L588)), and the frozen design choice is v8 discovery with limited v7 compatibility and ZIP 204 fallback ([section 8.3](https://github.com/zakura-core/zakura/blob/ac3078c0c06fc3868a10c38b7633d9d215e0b42f/docs/specs/fork-aware-header-chain-engine.md#L750-L757)). The transport layer already implements highest-common-version selection ([`selected_streams`](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-network/src/zakura/transport/registry.rs#L468-L491)), and its regression declares both v8 and v7 alternatives ([test](https://github.com/zakura-core/zakura/blob/139c4d1c3269421f616275986e760f23f4560925/crates/zakura-network/src/zakura/transport/registry.rs#L615-L635)). Production deliberately declares only v8. The PR's in-diff v1.4 rewrite removes compatibility, but under the requested authority order that edit cannot self-authorize the incompatible rollout.
- **Reproduction:** Run `cargo test -p zakura-network --locked supported_stream_accepts_registered_kinds_at_declared_version_only` to deterministically assert that v7 and bit 4 yield no header stream, then `cargo test -p zakura --locked stalled_zakura_without_legacy_fallback_keeps_waiting` to assert that the resulting Zakura-only stall never falls back. For an end-to-end reproduction, connect a `139c4d1` node configured with `p2p_stack = "zakura"` and a behind database only to an `ac3078c` peer on the same network; kind 5 is absent and the selected/verified tips do not advance.
- **Fix direction:** Preserve the frozen v7 capability/codec for a rolling compatibility window, declare both versions to the existing registry, and select the highest common version before decoding. Alternatively, make a proven standard-header fallback available in every supported upgrade configuration until v8 peers are guaranteed. Never route v7 bytes through the v8 decoder.
